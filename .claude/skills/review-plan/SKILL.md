  plan against current code, regression risks, edge cases, layer boundaries, and

  stress-test a plan before implementation. Returns the revised plan, not just
  findings; does not review a PR for merge readiness.

Review the plan for ticket $1 and incorporate the findings into a revised, executable plan. Use the same deep pass for an initial execution plan and a PR fix plan. No PR is required for an initial plan review.

**Argument guard.** The ticket argument is `$1`. Before anything else, confirm it is a single well-formed ticket id — `<PREFIX>-<number>` (e.g. `PROJ-312`). If it is empty, multi-word, or otherwise malformed (argument substitution can mangle multi-word invocations), do not use it verbatim: recover the intended id from the invocation text or the recent conversation. When the recovery is unambiguous, state which id you recovered and repeat that id in the final message so the user can catch a wrong guess. When several ids are plausible, or none can be recovered, ask the user with **AskUserQuestion** (only when there are 2–4 discrete choices; otherwise plain numbered questions): which ticket did you mean? Display the candidate ticket ids you found in the message body immediately before this question — asking without displaying it is non-compliant; never rely on earlier mid-turn text, and keep the question text itself short. A malformed id must never reach backend calls, branch names, or commit messages.

**Delegation contract** — applies whenever any part of this phase is delegated to a sub-agent or another model: sub-agents return data; every backend write (Linear artifact upsert, comment, state move, PR link) stays with you, the orchestrator, and happens in the main loop as soon as the delegated work returns — before the next phase begins. If a sub-agent must write instead, embed this skill's exact write instructions in its prompt (tool names, the artifact sentinel, the upsert-in-place rule). Either way, verify the writes landed (re-read the ticket) before moving on: a delegated run must leave the same trail on the ticket as a single-agent run.

## 1. Resolve the plan and its scope

- fetch the ticket with the Linear MCP **get_issue** tool (`id: $1`, `includeRelations: true`). This first Linear call doubles as the backend preflight: if the tool is missing or the call errors, **stop and tell the user** what the workflow needs — a Linear MCP server connected in your tool, exposing get_issue / list_issues / list_comments / list_milestones / save_issue / save_comment. Do not reconstruct ticket state from git alone and continue; a missing work artifact is recoverable; a missing backend is not.

- **Read the work artifact.** list the ticket's comments with the Linear MCP **list_comments** tool (`issueId: $1`) and find the one containing `<!-- ticket-flow:state v1 -->` — that is the work artifact. Use it as the authoritative scope (user stories, acceptance criteria, original plan, active Fix plan and scope selections, Plan review, branch, PR, code-review verdict). **Fallback chain — never hard-fail on a missing artifact:** if the artifact is missing or unparseable, reconstruct scope from the ticket description and from `git log`/`git diff` (the pre-artifact behavior); proceed with that and note you did. This fallback covers a missing **artifact** only — if the Linear MCP itself is missing or erroring, stop per the preflight (a missing work artifact is recoverable; a missing backend is not).

- Use the plan explicitly selected by the user (including a draft in chat or a supplied file); otherwise use the active, unfinished `Fix plan` when present, then the original `Plan`. If multiple candidates are plausible, ask which to review. If there is no plan, request one or hand off to `/describe-ticket $1`; do not pretend to have reviewed a missing plan.
- Carry forward the user-ratified stories, acceptance criteria, constraints, and deferrals. For a fix plan, also read the source findings and the user's selected scope. Do not silently reintroduce deferred findings or enlarge product scope.

## 2. Ground the review in current code

- Record the branch, commit SHA, and relevant uncommitted changes (`git status --short`, `git rev-parse HEAD`). Refresh remote refs where available and inspect the latest `origin/master`; for fixes, resolve the existing PR and its current head/base SHAs. Read the intended branch's files, not unrelated files from whichever branch happens to be checked out. Do not reset, switch over dirty work, or rebase just to review a plan.
- Read the affected implementation, callers, interfaces, existing tests, and repository guidance. Trace the behavior across the relevant layers. Verify proposed paths, symbols, assumptions, and test commands against those sources, citing repo-root-relative `file:line` evidence.
- Compare the plan's assumptions with changes since it was drafted and with relevant base-branch changes. Identify obsolete tasks, existing functionality to reuse, and newly exposed dependencies. If fresh remote code or a dependency cannot be inspected, state the baseline actually reviewed and the resulting limitation; never claim latest-code verification from stale refs.

## 3. Stress-test the plan

Cover each dimension with concrete findings and revisions, or evidence explaining why no change is needed:

- **Regressions and edge cases.** Follow each story or selected finding through affected callers and adjacent behavior. Consider applicable boundary values, empty/missing/invalid input, error propagation, retries/duplicate requests, concurrency, partial failure, permissions, compatibility, and recovery. Select cases from the actual code and ticket; do not turn every possible category into new scope.
- **Architecture and layer separation.** Put responsibilities in the repo's established layers, respect dependency direction and ownership, and reuse existing abstractions. Identify business logic leaking into UI/transport/storage layers, duplicated rules, inappropriate coupling, and interface or migration impacts. Propose the smallest sound design; a plan review does not authorize unrelated refactors.
- **Completeness and sequencing.** Map every acceptance criterion (or selected fix finding) to implementation tasks and verification. Include necessary call sites, failure paths, compatibility handling, and rollout/cleanup dependencies. Preserve completed work and expose unresolved decisions instead of burying them in implementation tasks.
- **Verification depth.** Inspect what proposed tests actually exercise and assert. Reject false greens (the test passes with the defect intact) and shallow greens (only smoke checks, snapshots, mocked return values, or call counts where observable behavior matters). Use the appropriate unit, integration, or end-to-end boundary; mocks must not replace the behavior under test. Check fixtures reach the intended path, assertions distinguish correct from plausible wrong behavior, async work is awaited, and negative cases verify side effects or their absence when relevant.

For each meaningful test, specify: the criterion/finding and risk; concrete setup/inputs; test file and layer; observable expected result; and the defect or regression that would make it fail. Pair reproducing tests with implementation tasks. For regressions, plan to observe failure with the defect present and success after the fix; for preserved behavior, identify the plausible breaking change the test would catch. Add broader gate and manual checks where automated coverage cannot establish the outcome, explaining the remaining gap. A larger test count alone is not evidence of depth. Planned checks are not executed checks: report commands actually run and their results separately, and never claim a red/green cycle happened during planning unless it did.

## 4. Incorporate and deliver the revised plan

- Integrate every supported, in-scope correction directly into the ordered plan, retaining task/story/finding IDs where possible. Return the **full revised plan**, with file pointers, test→implementation ordering, the verification cases above, and a concise account of what changed and why. Even when no corrections are needed, return the plan and the evidence supporting it.
- Mark the plan assessment **ready for execution** or **blocked**, with concrete unresolved decisions, coverage gaps, or baseline limitations. Ask only about decisions that cannot be resolved from code and the confirmed scope. Complete the independent review and revisions while those questions remain open; do not treat an unresolved choice as approved.
- For an existing work artifact, update only the selected `Plan` or `Fix plan` and its `Plan review` assessment: baseline SHAs/dirty state, target plan/revision, incorporated changes, verification matrix, and remaining limitations. Preserve the lifecycle status, original implementation history, PR link, scope selections, and `Review verdict`. For a fix plan, synchronize its own `blocked`/`planned` state with the assessment when decisions are resolved, retaining completed tasks and any executing/completed history. **Update the work artifact.** upsert the work-artifact comment: list the ticket's comments with the Linear MCP **list_comments** tool (`issueId: $1`) and find the one containing `<!-- ticket-flow:state v1 -->`; if found, **update it in place** with the Linear MCP **save_comment** tool (pass its comment id); if none exists, create it (`issueId: $1`). Never post a second copy — then **verify the write**: the response must contain the created/updated id; report it (with the ticket URL) in your summary. If the call fails or the tool is unavailable, stop and tell the user — never continue silently. Set `status`, tick the US-N / T-N checkboxes that are now done, refresh `updated`, and fill the `PR` / `Review verdict` sections as those become available. Preserve unrelated sections, including the original plan/history, `Fix plan`, and `Plan review`; change lifecycle status and code-review verdict only as directed by the current phase. Invalidate a plan assessment when its target plan or relevant code baseline changes unless this phase also refreshes the assessment against those changes. Then render the updated artifact sections (user stories / acceptance criteria / plan, plus the active fix plan and plan assessment when present, with current checkbox state) inline as part of your turn's final message, after all backend writes and tool calls — the user must never need to open the ticket to see current state. Text emitted between tool calls may not be displayed by the host; a render the user cannot see does not count.
- For an unratified Describe Ticket draft, return the revised draft for that skill's ratification step; do not create the artifact or branch early. An external plan with no artifact also returns as a revised draft until its scope is confirmed and recorded through describe-ticket or plan-fix.
- A plan assessment is **not** a code-review verdict. Never clear PR blockers or set `Review verdict` to ready to merge. Do not implement, commit, push, resolve PR threads, or merge as part of this skill.
- When an artifact is updated: **Checkpoint — do not hand off the revised plan until the revised plan and its assessment are receipted in the existing work artifact.** The work artifact is the phase gate: a phase is not complete until the ticket reflects it, and a write you cannot show a receipt for did not happen.


End with the revised plan, material changes, baseline, verification coverage, unresolved decisions, and ticket URL. Suggest `/execute-ticket $1` for an initial plan or `/execute-fix $1` for a fix plan when the plan is ready and its scope confirmed; otherwise state the specific next decision. Reviewing a plan does not itself authorize execution.

**End on the render.** In any turn that updated the work artifact, the artifact render must land in the turn's final message, after all backend writes and tool calls — never only in mid-turn text. A short closing pointer (e.g. the next step to run) may follow it within that same message; never end the turn on a bare receipt that points back at earlier, possibly hidden mid-turn text.
## Resume / idempotency

Re-read the latest plan and code each time. Update the same artifact sections, preserve completed checkboxes and scope decisions, and replace stale plan assessments when the code or plan changes. Re-review only needs new findings when there is new evidence; do not manufacture changes to make a second pass look productive.
