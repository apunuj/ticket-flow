# Ticket-Flow — ticket-driven workflow (Linear)

This project follows a ticket-driven workflow. **Recognize the user's intent from normal conversation and run the matching phase — they do _not_ need to type the slash command.** Each phase's full procedure lives in the linked file; open it and follow it. The slash command is just a shortcut to the same procedure.

- **Find the next ticket** — when the user asks what to work on, what's next, what's in the backlog, or which ticket to pick up. → `/next-ticket`
- **Describe / plan a ticket** — when the user wants a ticket turned into product behavior, acceptance criteria, and an execution plan, or says things like "plan PROJ-123", "break this ticket down", "what's the plan for this". → `/describe-ticket`
- **Review a plan** — when the user wants a deeper pass on an execution plan or fix plan: "review the plan", "stress-test this plan", "check edge cases and test depth". Revises the plan against current code, regressions, architecture, and verification. → `/review-plan`
- **Execute a ticket** — when the user wants to build a planned ticket or ship it (test gate → push → PR → move to In Review): "build PROJ-123", "implement this ticket", "start coding it", "ship it", "open a PR". → `/execute-ticket`
- **Review a ticket** — when the user wants the ticket's PR reviewed or checked against its acceptance criteria: "review the PR", "is PROJ-123 ready", "does this meet the criteria". → `/review-ticket`
- **Plan fixes for a ticket's PR feedback** — when the user wants to act on review comments or a failing/blocked PR: "fix the review comments", "address the PR feedback", "fix the failing CI on PROJ-123". Asks which findings to address, then records a fix plan without implementing it. → `/plan-fix`
- **Execute a fix plan** — when the user wants the selected fixes implemented on the existing PR: "execute the fix plan", "apply the reviewed fixes". Verifies and pushes fixes, then hands off for code re-review. → `/execute-fix`
- **Merge a ticket** — when the user wants to land/merge reviewed work and close out: "merge it", "land PROJ-123", "close out the ticket". → `/merge-ticket`
- **Orchestrate tickets** — when the user wants several tickets worked together and/or a multi-model split (one model plans + reviews, another builds): "work PROJ-101 and PROJ-102 together", "orchestrate these tickets". → `/orchestrate-ticket`

**Lifecycle order:** next → describe → review-plan → execute → review-ticket → merge. For open PR findings or red CI: plan-fix → review-plan → execute-fix → review-ticket. Review Plan is a reusable deeper pass on either plan; it returns a revised plan and never substitutes for code review. Plan Fix replaces the former fix-ticket command; fix execution belongs to execute-fix. The phases are idempotent and resumable: if an earlier phase was skipped, the later one falls back gracefully (e.g. execute cuts the branch if describe never ran). When the intent is ambiguous, ask which phase the user means before acting.

## Sub-agents & multiple tickets

- The lifecycle applies **per ticket**, regardless of who executes: N tickets in flight = N work artifacts, N branches, N state transitions — never a shared or skipped trail.
- Delegating a phase to a sub-agent does not skip that phase's procedure. Sub-agents return data; the orchestrator performs and verifies every backend write (artifact upsert, comments, state moves, PR links) when the delegated work returns — or embeds the phase's exact write procedure in the sub-agent's prompt and verifies the writes landed afterwards.
- Verify after everything: when delegated work returns, the orchestrator re-runs the test gate on the exact pushed tip and reads each CI check's conclusion individually — a sub-agent's report or a watcher's exit code is never the gate.
- Non-blocking review residuals accumulate in one numbered deferred-findings ticket per batch, referenced from PR bodies.
- Work tickets in dependency order (Blocked-by first) and summarize progress to the user at each ticket boundary.

## Feature record helpers

This pack was generated by Ticket-Flow **0.7.0**; feature records use
schema **1**. The stateless foundation exposes `hash`,
`pack-record`, `unpack-record`, and `validate` with typed JSON on stdin.

Use the matching installed package, or after that version is published:

```sh
npx --yes --package ticket-flow@0.7.0 ticket-flow feature <command> --input -
```

These helpers have no tracker access and retain no recovery state. They require no
consumer `package.json`. Exit 0 means valid supplied evidence, 2 means invalid input,
and 1 means an unexpected execution failure. Local validation does not establish
fresh remote reads, user consent, or a successful write. Tracker read-back and
approval remain the caller's responsibility.

CLI input is limited to 16 MiB. Packing returns `UNPACK_INPUT_LIMIT` (exit 2,
no result) if its compact unpack request cannot fit. Preparation is provisional;
finalize with actual part references and the same revision evidence before
publishing a descriptor. On failure, preserve the previous descriptor and pointer.
Send unpack requests as compact UTF-8 JSON without extra whitespace.

Feature conversation skills, domain-specific manifest/publication contracts, and
action gates arrive in later slices; this foundation does not enable those phases.
For an unreleased build, use its local installed executable or tarball rather than
falling back to an older registry version.
