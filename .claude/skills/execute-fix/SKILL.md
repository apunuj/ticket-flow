Execute the confirmed fix plan for ticket $1 on its existing PR.

**Argument guard.** The ticket argument is `$1`. Before anything else, confirm it is a single well-formed ticket id — `<PREFIX>-<number>` (e.g. `PROJ-312`). If it is empty, multi-word, or otherwise malformed (argument substitution can mangle multi-word invocations), do not use it verbatim: recover the intended id from the invocation text or the recent conversation. When the recovery is unambiguous, state which id you recovered and repeat that id in the final message so the user can catch a wrong guess. When several ids are plausible, or none can be recovered, ask the user with **AskUserQuestion** (only when there are 2–4 discrete choices; otherwise plain numbered questions): which ticket did you mean? Display the candidate ticket ids you found in the message body immediately before this question — asking without displaying it is non-compliant; never rely on earlier mid-turn text, and keep the question text itself short. A malformed id must never reach backend calls, branch names, or commit messages.

**Delegation contract** — applies whenever any part of this phase is delegated to a sub-agent or another model: sub-agents return data; every backend write (Linear artifact upsert, comment, state move, PR link) stays with you, the orchestrator, and happens in the main loop as soon as the delegated work returns — before the next phase begins. If a sub-agent must write instead, embed this skill's exact write instructions in its prompt (tool names, the artifact sentinel, the upsert-in-place rule). Either way, verify the writes landed (re-read the ticket) before moving on: a delegated run must leave the same trail on the ticket as a single-agent run.

## 1. Resolve the PR and confirmed fix plan

- read the ticket's attachments/links (Linear MCP **get_issue** on `$1`) and its comments (Linear MCP **list_comments**, `issueId: $1`) for the GitHub PR URL that execute-ticket attached; cross-check with `gh pr list --search "$1"` if missing. This first Linear call doubles as the backend preflight: if the tool is missing or the call errors, **stop and tell the user** what the workflow needs — a Linear MCP server connected in your tool, exposing get_issue / list_issues / list_comments / list_milestones / save_issue / save_comment. Do not reconstruct ticket state from git alone and continue; a missing work artifact is recoverable; a missing backend is not.

- If no PR is found, ask for its number or URL. If none can be supplied, stop: this skill requires an existing PR. Use `/execute-ticket $1` for initial implementation and shipping.
- **Read the work artifact.** list the ticket's comments with the Linear MCP **list_comments** tool (`issueId: $1`) and find the one containing `<!-- ticket-flow:state v1 -->` — that is the work artifact. Use it as the authoritative scope (user stories, acceptance criteria, original plan, active Fix plan and scope selections, Plan review, branch, PR, code-review verdict). **Fallback chain — never hard-fail on a missing artifact:** if the artifact is missing or unparseable, reconstruct scope from the ticket description and from `git log`/`git diff` (the pre-artifact behavior); proceed with that and note you did. This fallback covers a missing **artifact** only — if the Linear MCP itself is missing or erroring, stop per the preflight (a missing work artifact is recoverable; a missing backend is not).

- Read the `Fix plan`, its selected findings and source links, deferrals, tasks, verification cases, and `Plan review` assessment. If the fix plan or explicit scope selection cannot be recovered, hand off to `/plan-fix $1`; never infer permission to fix every open finding from the artifact fallback.
- Resolve any blocked plan, blocked plan assessment, or unconfirmed product decision before implementation. Honor the already confirmed scope; new findings return to scope selection rather than silently expanding this run.
- Inspect the PR's state, head branch/repository and head/base SHAs. If it is closed, merged, or belongs to another ticket, stop and resolve the target. Confirm it matches the fix plan; never create a replacement PR or branch.

## 2. Check out and revalidate

- Inspect `git status --short`, the current branch, and local commits. Safely check out the PR's actual head branch, preserving unrelated work. Do not derive a new branch name from the ticket or push directly to `master`.
- Re-read current findings, checks, and relevant code/tests. Compare the head/base SHAs and relevant dirty changes with the plan's baseline. If they changed, verify the tasks still apply and refresh stale plan-review evidence; use `/review-plan $1` if design or verification assumptions no longer hold.
- Skip an already addressed task only with current code/test evidence. If all fixes were already pushed, repair any missing recording steps below without duplicating commits, notes, or thread replies. A completed plan does not authorize another fix round or invalidate a newer successful code review.

## 3. Apply the selected fixes

Never post a second copy — then **verify the write**: the response must contain the created/updated id; report it (with the ticket URL) in your summary. If the call fails or the tool is unavailable, stop and tell the user — never continue silently. Set `status`, tick the US-N / T-N checkboxes that are now done, refresh `updated`, and fill the `PR` / `Review verdict` sections as those become available. Preserve unrelated sections, including the original plan/history, `Fix plan`, and `Plan review`; change lifecycle status and code-review verdict only as directed by the current phase. Invalidate a plan assessment when its target plan or relevant code baseline changes unless this phase also refreshes the assessment against those changes. Then render the updated artifact sections (user stories / acceptance criteria / plan, plus the active fix plan and plan assessment when present, with current checkbox state) inline as part of your turn's final message, after all backend writes and tool calls — the user must never need to open the ticket to see current state. ## 4. Verify and update the existing PR

- Run `npm test` as the final gate on the exact tip to be pushed. If it fails, report the failing output and stop before pushing or marking the fix plan complete. Never silently waive a failed gate.
- Commit any remaining scoped changes using the conventions above, then push to the **existing PR's head branch and repository**. Verify the destination before pushing, especially for a fork PR; do not open a new PR.
- Refresh the existing PR body with selected fixes mapped to findings, deferred items and reasons, verification results, and the updated work artifact. Preserve unrelated PR content.
- Confirm CI is running on the pushed head and report its actual state; pending is not passing.

## Stop and ask

- The PR target, file attribution, or ownership of local commits is ambiguous.
- A fix needs an unconfirmed product decision or exceeds selected scope.
- The test gate fails or the existing PR branch cannot be updated safely.

## Resume / idempotency

Re-read the artifact and live PR before resuming. Continue only unfinished selected tasks; if commits already exist locally, verify and push those rather than recreating them. If the fixes were pushed, complete missing receipts and thread updates, then re-review. Never redo completed tasks or reset the original implementation history.
