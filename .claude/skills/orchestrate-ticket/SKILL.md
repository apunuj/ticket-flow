Orchestrate ticket(s) $ARGUMENTS through the full lifecycle — describe → review-plan → execute → review-ticket → plan-fix → review-plan → execute-fix → re-review → merge — using sub-agents for the heavy phases while you, the orchestrator, keep every backend write.

**Argument guard.** The ticket list is `$ARGUMENTS`. Every whitespace-separated token must be a well-formed ticket id — `<PREFIX>-<number>` (e.g. `PROJ-312`). Drop anything else (words, paths, stray dashes) and recover the intended ids from the invocation text or conversation; state which ids you recovered and repeat them in the final message so the user can catch a wrong guess. If several ids are plausible, or none can be recovered, ask the user with the candidate ids displayed. A malformed id must never reach backend calls, branch names, or commit messages.

**Delegation contract** — applies whenever any part of this phase is delegated to a sub-agent or another model: sub-agents return data; every backend write (Linear artifact upsert, comment, state move, PR link) stays with you, the orchestrator, and happens in the main loop as soon as the delegated work returns — before the next phase begins. If a sub-agent must write instead, embed this skill's exact write instructions in its prompt (tool names, the artifact sentinel, the upsert-in-place rule). Either way, verify the writes landed (re-read the ticket) before moving on: a delegated run must leave the same trail on the ticket as a single-agent run.

**The delegation contract's embedded-write exception does not apply under orchestration** — the orchestrator keeps every backend write. Sub-agents never write to the backend, so you never embed this skill's write instructions in a sub-agent brief; every write happens in your main loop with a receipt.

## Model split

Which model runs each role is a cost/quality decision the operator owns — never resolve it silently. Resolution order: **explicit per-run instruction > config > ask**.

- **Per-run override.** A model split the user states in the invocation or the conversation wins over everything below, configured values included. It applies to this run only and skips any model-split question; it is never written back to config, and the kickoff summary must flag it as a one-run override.
- **Ask first.** No complete configured split (both roles must be set) — before any phase work, ask the user with **AskUserQuestion** (only when there are 2–4 discrete choices; otherwise plain numbered questions): which model split to use for this run — **Split** (recommended): the strongest model plans and reviews, the worker model builds and fixes; **All-strongest**: the strongest model for both roles; **Budget**: the worker model for both roles; **Custom**: name a model per role, with optional per-phase overrides. Do not proceed until the user has answered.
- **Pin on spawn.** Pin the resolved model on each sub-agent spawn where your tool supports it; otherwise record the chosen split in the sub-agent brief and the kickoff summary and proceed.
- **Kickoff summary.** Open the run by naming the resolved split and where it came from (per-run instruction, config, or the user's answer). The kickoff summary and every boundary summary must name which model ran each phase.
- **Persist offer.** The rule: **the persist offer fires only when the split came from the interactive ask — never after a per-run override, never for a config-pinned split.** When it fires, offer to save the split to the `orchestrate` config block only **after the run completes** — at the final boundary summary, back on the base branch. Never edit the config mid-run, and never write the choice back silently.

## Roles

- **Planner** — plans and reviews; runs on the Planner model resolved above. Owns the describe-phase analysis, both plan-review passes, fix planning, and the code-review findings.
- **Implementer** — builds and fixes; runs on the Implementer model resolved above. Owns code, tests, and commits on the ticket branch.
- **You (orchestrator)** — sequencing, every Linear write (with receipts), git/PR operations, and all user interaction.

## Sub-agent briefs

If your tool has no sub-agent primitive, run each role yourself — role-switch between the Planner and Implementer phases in your own loop, keeping every backend write with you; the briefs below then become your own per-phase checklists.

Sub-agent prompts must embed the relevant phase skill's procedure — read the phase skill file and carry its instructions verbatim where the sub-agent needs them; sub-agents return their results as data. Every brief must:

- Point at the finalized plan artifact and the user-ratified decisions, stating explicitly that those decisions **override** the raw ticket text where they differ.
- State the scope boundary — what belongs to this ticket's PR vs later tickets — and that sub-agents never push, open PRs, or write to the ticket backend.
- State the gates and exact baselines (e.g. the test count to beat) and the commit conventions.
- Require a structured return: per-task status, files touched, final gate numbers, deviations, commit SHAs, unresolved forks.
- Instruct stop-and-return on a genuine product fork — a sub-agent can never reach the user.

## Interaction contract

Exactly two classes of questions reach the user **mid-run** (the model-split resolution above and the persist offer sit outside it, at the run's open and close); everything else runs autonomously:

1. **Product clarifications and plan ratification** during planning (describe's clarifying questions — batch them per ticket; then the plan ratification STOP); the bubbled message itself must display the Planner's summary, user stories, and acceptance criteria — sub-agent output is invisible to the user unless you relay it.
2. **Judgment calls on review findings** (fix now / skip / defer — present the Planner's findings grouped, with your recommendation); the bubbled message itself must display every finding — grouped blocking vs nice-to-have, each with its `file:line` and your recommendation — in the message body immediately before the question — asking without displaying it is non-compliant; never rely on earlier mid-turn text, and sub-agent output is invisible to the user unless you relay it.

Hard gates still stop the run: a failing test gate, merge confirmation (waivable only per the dormant-vs-live rule in lifecycle step 5 — a dormant, flag-gated change may merge under standing authority; a live-behavior change always re-confirms), stacking approval before branching one ticket off another, destructive actions, and anything the phase skills mark "stop and ask".

## Ordering

Fetch every ticket up front (fetch the ticket with the Linear MCP **get_issue** tool (`id: <ticket-id>`, `includeRelations: true`) for each id — this doubles as the backend preflight; if the tool is missing or erroring, stop and tell the user). Resolve the dependency order: `Blocked-by` relations and description chains. A blocked ticket waits until its blocker is **merged**, not merely built. Escape hatch: if the blocker's merge is held by something external (e.g. a deploy prerequisite) and the user approves, stack — branch the next ticket off the blocker's branch and keep building; once the blocker merges, rebase onto the base branch (`git rebase --onto origin/master <old-base>`) and retarget the PR. Work strictly one phase of one ticket at a time — except under the approved stacking hatch above, where building the stacked ticket may proceed on its branch — and otherwise do not interleave phases across tickets.

## Per ticket — the standard lifecycle, delegated

Each ticket gets its own artifact, branch, and state transitions — never shared, never skipped.

1. **Plan (Planner).** The Planner returns product behavior, user stories, acceptance criteria, clarifying questions, and a draft test-driven plan as data. Bubble the clarifying questions to the user (STOP class 1): ask the Planner's clarifying questions as **plain numbered questions in the message body, not through a question dialog**, and end the turn on them: the message is the Planner's summary, user stories, and acceptance criteria, followed by the numbered questions as its last lines. Hosts can hide text that precedes a tool call, so a dialog would leave the user answering questions about content they never saw. Asking through a dialog here is non-compliant. After answers (or immediately when no clarification is needed), the Planner runs `/review-plan` on the draft against current code, incorporating regression, architecture, and verification improvements; then — even when there were no clarifying questions — display the refined user stories and the execution plan and STOP for the user to ratify them (no trivial-clarifications escape). Only after ratification do **you** write the work artifact with `status: planning` — **Update the work artifact.** upsert the work-artifact comment: list the ticket's comments with the Linear MCP **list_comments** tool (`issueId: <ticket-id>`) and find the one containing `<!-- ticket-flow:state v1 -->`; if found, **update it in place** with the Linear MCP **save_comment** tool (pass its comment id); if none exists, create it (`issueId: <ticket-id>`). Never post a second copy — then **verify the write**: the response must contain the created/updated id; report it (with the ticket URL) in your summary. If the call fails or the tool is unavailable, stop and tell the user — never continue silently. Set `status`, tick the US-N / T-N checkboxes that are now done, refresh `updated`, and fill the `PR` / `Review verdict` sections as those become available. Preserve unrelated sections, including the original plan/history, `Fix plan`, and `Plan review`; change lifecycle status and code-review verdict only as directed by the current phase. Invalidate a plan assessment when its target plan or relevant code baseline changes unless this phase also refreshes the assessment against those changes. Then render the updated artifact sections (user stories / acceptance criteria / plan, plus the active fix plan and plan assessment when present, with current checkbox state) inline as part of your turn's final message, after all backend writes and tool calls — the user must never need to open the ticket to see current state. Text emitted between tool calls may not be displayed by the host; a render the user cannot see does not count. — and check out the ticket branch per `/describe-ticket`.
2. **Build (Implementer).** First the build-start gate from `/execute-ticket`: artifact to `status: building`, then move the ticket to **In Progress** with the Linear MCP **save_issue** tool (`id: <ticket-id>`, `state: "In Progress"`) — then **verify the write**: the response must contain the created/updated id; report it (with the ticket URL) in your summary. If the call fails or the tool is unavailable, stop and tell the user — never continue silently. Only then spawn the Implementer on the ticket branch; it works the plan test-first and returns commits + test results as data. **You** run the test gate, push, open the PR — verifying independently: re-run the full test gate on the exact tip being pushed (never trust the Implementer's reported numbers alone) and confirm a clean tree — then complete `/execute-ticket` step 5: attach the PR, post the shipping note, move to In Review, update the artifact.
3. **Review (Planner).** **Orchestrate resolves review depth itself — default high; a per-run instruction in the invocation can override.** Resolve the depth before spawning and pass it to the Planner in the brief; the Planner reviews at that depth and does not ask. The Planner reviews the PR against the acceptance criteria and returns a verdict + findings as data. **You** record the review comment and the artifact's `Review verdict` per `/review-ticket` — which always posts the findings as inline PR comments. If there are open findings or failing checks, continue to fix planning; otherwise proceed to merge.
4. **Plan and execute fixes.** The Planner runs `/plan-fix` to gather and deduplicate current findings, unresolved threads, CI failures, and conflicts. **You** bubble the triage to the user (STOP class 2): ask the user with **AskUserQuestion** (only when there are 2–4 discrete choices; otherwise plain numbered questions): which to fix now / skip / defer. Display every finding — grouped blocking vs nice-to-have, each with its `file:line` (or check/source link) and your recommendation — in the message body immediately before this question — asking without displaying it is non-compliant; never rely on earlier mid-turn text, and keep the question text itself short. Reuse scope already explicitly selected in this run; do not ask twice. Findings the user defers go to **one deferred-findings ticket for the whole batch** — create it on first use (create a new issue with the Linear MCP **save_issue** tool (omit `id` to create; `title: <title>`, `description: <description>`) in the active Linear team/project for this repo (ask if ambiguous), and note the new issue's id from the response — then **verify the write**: the response must contain the created/updated id; report it (with the ticket URL) in your summary. If the call fails or the tool is unavailable, stop and tell the user — never continue silently), number findings sequentially as they accumulate, and reference it from each PR body. A deferred blocker still blocks merge until re-review explicitly resolves its impact; deferral alone never clears it.
   - **Planner:** produce the selected fix plan, then run `/review-plan` and return the revised plan with concrete regression tests and remaining decisions. **You** record the `Fix plan` and `Plan review` sections, preserving the original plan and code-review verdict. Bubble unresolved product decisions before execution; a ready plan assessment does not make the PR ready to merge.
   - **Implementer:** follow `/execute-fix` for the revised plan. **You** own its backend writes, check out the existing PR branch, invalidate the prior verdict, and verify the full test gate on the exact tip before pushing to that PR. Record fixed/remaining items and verification evidence; never create a replacement PR.
   - **Planner:** after fixes, **spot-verifies each applied fix** — it resolves its finding, introduces no new bug or regression, and breaks no interface a downstream ticket depends on — then re-review per step 3 until the verdict is ✅. New findings return to scope selection, not automatic scope expansion.
5. **Merge.** Confirm with the user — unless standing merge authority covers this change per the dormant-vs-live rule below — then follow `/merge-ticket`: review gate, merge, closing comment, done state, artifact `status: merged`, cleanup. Before merging, watch CI to completion and read each check's conclusion individually — never trust a watcher's exit code alone. When the user has granted standing merge authority, distinguish dormant from live: a flag-gated change that deploys inert may merge without a fresh confirm; a change that alters live production behavior always gets an explicit confirm plus a prerequisites checklist in the PR body.
6. **Boundary summary.** Before starting the next ticket, report: ticket → PR → verdict → state, with receipts (comment ids / URLs) and the model that ran each phase.

**Checkpoint — do not start any phase of the next ticket until the previous phase's backend writes are receipted on the current ticket.** The work artifact is the phase gate: a phase is not complete until the ticket reflects it, and a write you cannot show a receipt for did not happen.

## Resume / idempotency

Re-running with the same ticket list resumes each ticket from its artifact `status` (planning → building → in-review → merged) — never redo a receipted phase, never post a duplicate artifact. For `in-review` tickets, inspect the `Fix plan` state and unfinished tasks before treating execution as complete; resume planning, plan review, or fix execution as appropriate.
